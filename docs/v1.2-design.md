# v1.2 design contract

Issues #31 (ports), #32 (UniFi DNS), #33 (images and memory). Coordinator-owned; every v1.2
agent builds against this text and `docs/stack-design.md`.

## 1. TrueNAS web UI ports and the port inventory (#31)

- The guide no longer moves the TrueNAS UI. It reads the current ports (**System** >
  **General Settings** > **GUI**, verified for 25.10) and requires only that 80 and 443 (tcp, and
  443/udp) are free for Caddy. The owner's UI is on 444 (HTTPS) and 81 (HTTP redirect); the guide
  uses `<ui-https-port>` with 444 as the worked example, and still offers moving the UI when 80/443
  are taken by it.
- `tools/port-inventory.sh` (new, POSIX sh, read-only, runs in the TrueNAS shell from the clone,
  needs sudo only for socket owner names): prints one table of listening TCP/UDP sockets (port,
  protocol, address, process), Docker-published ports per container, and the TrueNAS app
  of each container (from its Compose project label `ix-<app>`); the UI ports come from
  `midclt call system.general.config`, then a verdict per port the
  stack needs: `free`, `used by <who>`. Exit 0 when every needed port is free, 1 otherwise.
  Ports the stack needs on the host: 80/tcp, 443/tcp, 443/udp (Caddy) and nothing else; the UI
  ports are reported for information. Shellcheck-clean; a unit test with fixture command output.
- `deploy.py` and `deploy/truenas.toml`: the API URI carries the UI HTTPS port; examples use
  `wss://192.0.2.10:444/api/current`.

## 2. DNS on a UniFi UDM-Pro SE (#32)

- Split horizon. Public Cloudflare zone: no lab records (Caddy adds and removes ACME TXT records).
  UDM: local records for `chat`, `llm`, `models`, `mcp`, `search` under the lab domain (or a
  wildcard, if UniFi supports it) → the TrueNAS IP. Clients use the UDM as their DNS server.
- Research note `docs/research/g-unifi-dns.md` decides the exact UI path and options in the
  current UniFi Network application for the UDM-Pro SE, wildcard support, ad-blocking/content
  filtering and DNS rebinding effects, DoH on clients (browsers bypassing the UDM), and IPv6.

## 3. Images and memory (#33)

- `coder` loads its projector on the CPU: `--mmproj /models/gguf/<mmproj file> --no-mmproj-offload`
  (verify flag names at llama.cpp b12407); context stays 64K; `coder-fast` is the same process, so
  it sees images too. `coder-moe` gets its own projector the same way if a file exists for it.
  Projector files are added to `stack/inference/models.tsv` and `models.sha256` with revision and
  hash from the Hugging Face API.
- LiteLLM: the client names backed by `coder` declare vision support so clients send images.
- Open WebUI: Memory feature on (verify the variable/setting in 0.13.3 and whether it is a user
  setting); files dropped into a chat stay with that chat (the default); no automatic adding to a
  knowledge base.
- OpenCode: `local-coder` and `local-fast` declare image input (verify the `modalities` key);
  Claude Code: images pasted or dropped are sent as image blocks to `/v1/messages`.
- Evals: one image case in the format suite (a bundled PNG with known text), marked optional
  until verified on the server.
